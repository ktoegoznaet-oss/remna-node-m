# Remnawave Node за одним портом 443

Конфигурация ноды Remnawave, где весь клиентский трафик входит через
**единственный публичный порт 443**, а nginx разводит его по трём инбаундам
Xray по имени из TLS ClientHello. Нестандартные порты наружу не торчат
вообще.

---

## Как это устроено

```
                        публичный интерфейс
                               │
                          443/tcp (nginx)
                               │
                   читает SNI из ClientHello
                        (ssl_preread)
                               │
        ┌──────────────────────┼──────────────────────┐
        │                      │                      │
  SNI = SNI_TCP          SNI = SNI_GRPC        SNI = SNI_XHTTP
        │                      │                      │
  127.0.0.1:4433         127.0.0.1:5443         127.0.0.1:8443
  VLESS RAW              VLESS gRPC             VLESS XHTTP
  + Reality (Vision)     + Reality              + Reality
        │                      │                      │
        └──────────────────────┴──────────────────────┘
                               │
                         remnawave/node
                               │
                      2231/tcp ── панель Remnawave
                                  (только с её IP)
```

nginx работает на четвёртом уровне. Он **не расшифровывает трафик**: читает
незашифрованное поле SNI из TLS ClientHello и пересылает поток целиком.
Сертификаты, ключи и Reality остаются на стороне Xray. Поэтому в конфиге
nginx нет ни `ssl_certificate`, ни `listen 443 ssl`, ни `http {}` — и не
должно быть.

### Ключевой момент, на котором ломается большинство инструкций

При **Reality** клиент отправляет в SNI не ваш домен, а **маскировочный
сайт** из `realitySettings.serverNames` — `opensuse.org`, `www.cloudflare.com`
и так далее. Домена вашей ноды в ClientHello нет вообще.

Отсюда два следствия:

1. Ключами в таблице маршрутизации nginx должны быть **маскировочные
   домены**, а не `node-a.example.com`. Инструкции, где в `map` стоят домены
   ноды, написаны под инбаунды с обычным TLS и с Reality не работают.
2. У каждого инбаунда должен быть **свой уникальный** маскировочный домен.
   Два инбаунда с одинаковым `serverNames` неразличимы для nginx —
   он просто не стартует с ошибкой `duplicate parameter`.

Чтобы это не разъезжалось, `nginx.conf` и `xray-config.json` генерируются
из одного `.env` скриптом `configure.sh`, который заодно проверяет
уникальность доменов и портов.

## Быстрый старт

```bash
git clone https://github.com/ktoegoznaet-oss/remna-node-m.git /opt/remnanode
cd /opt/remnanode

cp .env.example .env
chmod 600 .env

# 1. Сгенерировать ключи Reality и shortId (публичные ключи — выписать!)
sudo ./scripts/gen-reality-keys.sh --write

# 2. Заполнить остальное: SECRET_KEY из панели, PANEL_IP, три домена SNI_*
nano .env

# 3. Развернуть
sudo ./scripts/install.sh

# 4. Закрыть всё лишнее
sudo ./scripts/firewall.sh

# 5. Проверить
./scripts/check.sh
```

Дальше — настройка в панели: [docs/PANEL-SETUP.md](docs/PANEL-SETUP.md).
**Не забудьте выставить в хостах порт 443** — это то поле, из-за которого
схема чаще всего «не работает».

```
.
├── docker-compose.yml              контейнеры remnanode и nginx (host-сеть)
├── .env.example                    все параметры с пояснениями
│
├── nginx/
│   └── nginx.conf.template         L4-маршрутизация по SNI
├── xray/
│   └── xray-config.json.template   три инбаунда для вставки в панель
│
├── scripts/
│   ├── install.sh                  развёртывание с нуля
│   ├── gen-reality-keys.sh         ключи x25519 и shortId
│   ├── configure.sh                шаблоны + .env -> боевые конфиги
│   ├── check.sh                    диагностика
│   ├── trace.sh                    живой просмотр: какой SNI куда уходит
│   ├── firewall.sh                 правила ufw
│   └── tune-sysctl.sh              сетевой тюнинг хоста (BBR и прочее)
│
└── docs/
    ├── PANEL-SETUP.md              что настроить в панели Remnawave
    └── TROUBLESHOOTING.md          разбор типовых проблем
```

Боевые `nginx/nginx.conf`, `xray/xray-config.json` и `.env` в репозиторий не
коммитятся — они содержат ключи и генерируются на конкретном сервере.

## Что здесь сделано осознанно

**Инбаунды слушают `127.0.0.1`.** Не `0.0.0.0` плюс фаервол, а именно
loopback. Фаервол — второй слой, а не единственный. Если инбаунд доступен
снаружи напрямую, клиент обходит маршрутизацию по SNI, и весь смысл схемы
теряется.

**Включён PROXY protocol.** Без него Xray видит источником `127.0.0.1`: в
панели все пользователи онлайн с одного адреса, не работают лимиты по
устройствам и геороутинг. Требует `acceptProxyProtocol: true` в `sockopt`
каждого инбаунда — `configure.sh` проставляет это сам. Побочный эффект
полезный: к бэкенд-порту нельзя подключиться без PROXY-заголовка.

**`network_mode: host` для обоих контейнеров.** nginx должен ходить на те же
`127.0.0.1:порт`, которые слушает Xray. С bridge-сетью и пробросом портов
это не работает, а ещё добавляет лишний NAT.

**`worker_connections 16384`, а не дефолтные 1024.** На L4-прокси одно
клиентское соединение занимает два слота — к клиенту и к бэкенду. 1024
даёт потолок примерно в 500 клиентов на воркер.

**`proxy_timeout 1h`.** Меньше ставить не стоит: idle-сессии мессенджеров,
SSH и открытых вкладок будут рваться, и пользователь увидит это как
«интернет отваливается».

**Неизвестный SNI уходит в `default`** — на Reality-инбаунд. Тот не пройдёт
проверку и прозрачно отдаст соединение настоящему сайту-маске. Для сканера
сервер выглядит обычным веб-сервером.

**Сниффинг с `routeOnly: true`.** Вынюханный домен используется только для
правил роутинга и не подменяет адрес назначения.

## Безопасность

Наружу открыты ровно три вещи:

| Порт | Кому | Зачем |
|---|---|---|
| `22/tcp` | только с `ADMIN_IP` | администрирование |
| `443/tcp` | всем | клиентский трафик |
| `2231/tcp` | только с `PANEL_IP` | управление нодой из панели |

Порт управления нодой нужен **всегда** — панель ходит на ноду именно по
нему. Формулировки вида «открывать при необходимости» неверны: без него
нода будет offline. Его нужно не «открыть по необходимости», а ограничить
одним IP. Ещё надёжнее — увести связку панель ↔ нода в WireGuard и не
светить порт в интернете вовсе.

Бэкенд-порты `4433`, `5443`, `8443` наружу закрыты дважды: `listen`
на loopback и явный `deny` в ufw.

> **Если ключи Reality где-то засветились — в переписке, в тикете, в
> скриншоте — считайте их скомпрометированными и перевыпустите:**
> `./scripts/gen-reality-keys.sh --write && ./scripts/configure.sh`.
> После этого обновите публичные ключи и shortId в хостах панели, иначе
> клиенты отвалятся.

`.env` держите с правами `600`. В git он не попадает.

## Чего в этой схеме быть не должно

Для L4-проксирования по SNI не нужны и только мешают:

* `listen 443 ssl` в nginx;
* `ssl_certificate` / `ssl_certificate_key` в `stream`;
* `proxy_ssl_*`;
* блоки `http {}` и сайты-заглушки.

nginx не терминирует TLS. Сертификаты живут на стороне Xray/Reality.
Отдельный веб-сайт на этом же сервере поднять можно, но к SNI-маршрутизации
Remnawave он отношения не имеет и потребует другой схемы.

## Про количество инбаундов

Здесь развёрнуты три: RAW+Vision, gRPC и XHTTP. Это больше ключей, больше
доменов-масок и больше поверхности атаки.

Практический минимум, который закрывает почти все задачи:

* **VLESS RAW + Reality + XTLS Vision** — основной, лучшая
  производительность;
* **VLESS XHTTP + Reality** — запасной для сетей с агрессивным DPI, где
  длинные TLS-сессии режутся.

gRPC сегодня даёт мало. Если решите его убрать — удалите инбаунд из
`xray/xray-config.json.template`, строку из `map` в
`nginx/nginx.conf.template`, соответствующие переменные из `.env` и
проверки из `configure.sh`.
